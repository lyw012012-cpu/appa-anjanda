# 시스템 제약 (검증 체계)

> 코드가 "끝났다"고 말하기 전에 통과해야 하는 검증. 무엇을 막는지(규칙)는 [architecture/](../architecture/README.md), 테스트 대상의 근거는 [context/design.md 5절](../context/design.md#5-테스트-전략). 플랫폼·OS·일정 한계는 [context/design.md 1.4~1.6절](../context/design.md#14-드라이버).

상태: ✅ 적용됨 / ⚠️ 있지만 실패 중 / ⬜ 제안·미정

## 1. 타입 검사와 린트

| 대상 | 명령 | 상태 |
|---|---|---|
| 앱 | `cd app && npm run check` (`tsc --noEmit` → `expo lint`) | ✅ |
| 아키텍처 규칙 | 같은 명령. [architecture/](../architecture/README.md) M1~M4가 ESLint에 들어 있음 | ✅ |
| AI (Python) | 정하지 않음 | ⬜ |

## 2. 자동 검증 테스트 (추천안, 팀 확정 전 · contracts 10절)

| 대상 | 도구 | 데이터 | 상태 |
|---|---|---|---|
| 점수·익숙함 판정 함수 (design.md 4.1·4.2) | jest-expo | contracts 8절 가짜 데이터와 기대 결과 | ⬜ |
| 최근 3회 재생한 소리 제외 (Q4) | jest-expo | 가짜 이벤트 | ⬜ |
| `sounds.json` 모양 (C2), 소리 ID 형식 | 앱: jest-expo, 파이프라인: pytest | 파이프라인 출력 | ⬜ |
| 특징 추출 (`ai/src`) | pytest | 짧은 예제 wav | ⬜ |

E2E는 하지 않는다. 합성·가짜 데이터 테스트로 확인되는 것은 "코드가 맞게 계산한다"까지다.

## 3. 검증 다각화

한 가지 검증에 기대지 않고, 같은 규칙을 **여러 층에서** 확인한다.

| 층 | 무엇을 잡나 | 언제 | 상태 |
|---|---|---|---|
| 타입 (`tsc`) | 계약 모양(C4 공유 타입)이 어긋난 코드 | 저장·커밋 전 | ✅ |
| 린트 (ESLint) | 금지 import, 의존 방향 (architecture.md M1~M4) | 커밋 전 | ✅ |
| 단위 테스트 | 계산이 틀린 코드 | 커밋 전 | ⬜ |
| 양쪽 검사 | `sounds.json`을 **쓰는 쪽(파이프라인)과 읽는 쪽(앱 로더)이 각각** C2 규칙 검사 | 생성할 때·앱 시작할 때 | ⬜ |
| CI | 위 검사를 PR마다 자동 실행 (GitHub Actions) | PR | ⬜ 없음 |
| PR 리뷰 | 도구로 못 막는 규칙 (M8 등), 계약 변경 | 병합 전, 팀원 1명 이상 | ✅ |
| 실기기 확인 | 알람 지연(Q1), 계산 시간(Q2), 시연(Q5) | 마일스톤마다, 표로 기록 | ⬜ |
| 실험 | `[가설]` 값이 맞는지 (E1~E5) | design.md 6절 일정 | ⬜ |

"완료"라고 말하기 위한 조건과 증거 기록 방법은 [AGENTS.md 0절](../../AGENTS.md)에 있다.
