# AI 설계: 사용자에게 맞는 알람 소리 찾기 [초안]

> 핵심: **YAMNet이 소리를 이해하고, 밴딧이 사람을 이해한다.** 사람마다 "어떤 성질의 소리가 나를 깨우나"를 반응 기록으로 학습하고, 알람 한 번에 소리 3개를 편안함 → 대비 → 낯섦 순서로 들려준다. 사람마다 다른 것은 **소리(밴딧)**와 **구조(설정·규칙)** 두 층으로 맞춘다.

- 상태: 2026-11-18 대화로 정한 초안. **팀 확인 전.** [design.md](design.md) AD2(학습 없음)와 1.1 범위를 바꾸는 제안이라, 팀이 받아들이면 design.md·[contracts.md](contracts.md)를 `docs(contract):` PR로 고친다(9절).
- 표시: **[확정]** 사용자가 정함 / **[제안]** 아직 미확정 / **[미확인]** 문서·실기기로 확인 안 함 / **[가설]** 실험·시뮬레이션으로 바뀔 값

## 1. 왜 바꾸나

| 문제 | 지금 설계 | 이 문서 |
|---|---|---|
| 공모전 조건: AI 서비스, 일상 문제를 AI로 해결 [확정] | AI는 소리 이해(YAMNet)에만 쓰고, 익숙함 판단과 소리 선택은 사람이 정한 식 | 소리 선택의 핵심(이 사람을 무엇이 깨우나)을 AI가 학습 |
| 사람마다 잘 깨우는 소리가 다름 [확정] | 520 Hz 유사도가 모두에게 같은 고정 점수. 바로 끈 기록(좋은 반응)은 버림 | 사람별 학습. 520 Hz는 시작값으로만 씀 |
| 혐오감 없이 깨워야 함 [확정] | 없음 | 거슬림 점수 상한 + "이 소리 빼기" |
| 못 깰 걱정이 없어야 함 [확정] | 알람 한 번에 소리 하나, 끄면 끝 | 알람 한 번 안에서 단계별로 소리를 바꾸고, 끈 뒤에도 다시 잠들었는지 확인 |

## 2. 목표

- **목적** [확정]: 혐오감을 주지 않는 적절한 소리로 편안하게 깨우되, 반드시 깨게 한다. 둘이 부딪히면 **반드시 깨는 쪽이 먼저**.
- "적절한 소리" = **잘 깨우는 소리** [확정]
- 흐름 [확정]: ① 사용자가 마음에 드는 소리 선택 → ② 알람에서 깨는 반응 확인(몇 번째 소리에서 몇 초 만에, 끈 뒤 다시 잠들었나) → ③ 기록 축적 → ④ 소리 분배로 제공 → ②로 반복

**하지 않음** [확정]
- YAMNet 파인튜닝·재학습: 데이터 15~30개로는 결과가 거의 안 바뀌고, 휴대폰에서 신경망을 돌리지 않으므로(M1) 사람마다 할 수도 없다
- 학습을 위한 학습: 거리 보정·거슬림 예측 학습은 넣지 않는다. 거슬림은 사람 평가로 **확인만** 하고, 크게 어긋날 때만 학습을 검토한다
- **끄기 미션**: 편안함과 일정 때문에 뺀다. "정말 깼나"는 상태 질문과 재확인(6.7)이 맡는다. 선택 기능으로 켜는 미션은 다음 단계
- 새 소리 생성(생성형 AI), iOS

**실패로 보는 것** (기술적으로 돌아가도)
- 사용자가 거슬려서 볼륨을 줄이거나 앱을 지운다
- AI의 시도 때문에 중요한 날 늦잠을 잔다
- 잠결에 끄고 다시 잠든 것을 "잘 깼다"로 배워 엉뚱한 소리를 강화한다
- 평균적인 사람에게만 맞고, 잠이 깊거나 예민한 사람에게는 매일 안전장치나 거친 소리가 울린다(5절)

## 3. 제약

- 휴대폰에서 신경망 금지(M1). 앱은 작은 행렬 연산만 한다
- 추천은 순수·결정적 함수(M2). 무작위를 쓰려면 시드를 입력으로 받는다
- 서버 연산 없음. Firestore는 보관용, 앱은 읽지 않음(M3)
- 기록은 대회 기간에 사람당 단계 기록 20~40개. 특징이 많으면 가중치가 시작값 근처에 머문다 [가설, 시뮬레이션으로 확인]. 효과는 증명할 수 없고, 가짜 데이터로 효과를 주장하지 않는다(design.md 1.5)
- 마감 2026-11-22. 13절 MVP 밖은 한계로 기록한다

## 4. 방법 비교

| 방법 | 내용 | 판단 |
|---|---|---|
| **A. 선형 Thompson sampling 밴딧** | 소리 특징 몇 개에 대한 "깨우는 정도" 가중치를 사람마다 베이지안 선형 회귀로 학습. 반응 하나마다 갱신 | **[확정] 채택.** 데이터가 적어도 동작, 가중치를 화면 설명으로 쓸 수 있음, 휴대폰에서 행렬 연산만 |
| B. 가우시안 프로세스 밴딧 | 특징 없이 YAMNet 거리만으로 "비슷한 소리면 결과도 비슷" | 설명이 어렵고, 음높이에 둔한 YAMNet 거리(6.2)에 전부 기댐 |
| C. 오프라인 분류기 | 모은 기록으로 PC에서 학습 | 데이터 부족, 사람마다 맞춰지지 않음, 가짜 데이터 학습은 규칙 위반 |

## 5. 사람마다 다른 경우 (설계 점검 기준)

이 설계는 아래 유형 각각에서 확인한다. 9절 시뮬레이션의 가상 사용자도 이 표에서 고른다.

| # | 유형 | 이 설계가 하는 일 | 남는 위험 |
|---|---|---|---|
| ① | 잠이 깊은 사람 | 대부분 3단계에서 깸. 최근 기록이 그렇으면 2단계부터 시작(7.2) | 낯선 소리를 빨리 소진, 안전장치가 일상이 됨 → 안전장치 비율을 지표로 봄 |
| ② | 잠이 얕은 사람 | 1단계 몇 초 만에 깸. 시작 음량을 직접 정함(7.1) | 편안한 소리 안에서만 배움(문제 적음) |
| ③ | 늘 스누즈하는 사람 | 상수항이 이 사람의 기본값을 흡수해 소리 학습은 유지. 스누즈 상한 | 잠결 스누즈를 막는 장치 없음(미션 뺌). 스누즈 비율이 높으면 "습관일 수 있어요" 안내 |
| ④ | 잠결에 끄고 다시 자는 사람 | 끄는 순간은 못 막음. 재확인(6.7)이 몇 분 뒤 잡아 다시 깨우고 보상을 낮춤 | 재확인까지 몇 분은 다시 잠 |
| ⑤ | 수면이 불규칙한 사람 | 날마다 결과가 크게 흔들려 학습이 느림 | **한계로 기록** |
| ⑥ | 고음이 잘 안 들리는 사람(난청·고령) | 음높이 특징으로 "저음에 잘 깸"을 배움. **개인화가 가장 효과 있는 경우** | 음높이 특징이 빠지면 못 배움 → 필수 특징(6.3) |
| ⑦ | 소리에 예민·불안한 사람 | "이 소리 빼기"가 비슷한 소리까지 피함. 부드러운 모드(대비 폭 축소). 재확인은 진동만 | 거슬림 점수(평균적 경향)가 이 사람에겐 안 맞음 |
| ⑧ | 한 계열만 고른 사람 | 처음 설정에서 서로 다른 계열 2개 이상 권장 | 그 계열 전체가 함께 익숙해짐 |
| ⑨ | 소리를 안 고른 사람 | 520 유사도 순으로 시작, 1단계 거슬림 상한이 거친 소리를 막음 | 시작값이 맞는지 시뮬레이션으로 확인 |
| ⑩ | 낮잠에도 쓰는 사람 | 알람에 아침/낮잠 구분, 낮잠은 학습에서 뺌 | (MVP 밖) |
| ⑪ | 몇 달 쓴 사람 | 익숙함이 시간에 따라 회복되어 순환 | "바뀌는 알람" 자체에 적응할 수 있음(탈습관화의 습관화). 목록 확대만이 근본 대책 → **한계로 기록** |

## 6. 오프라인 파이프라인 (팀 PC, `ai/`)

원칙 [확정]: **모델의 입력 규격을 먼저 정하고 데이터를 거기에 맞춘다.**

### 6.1 환경 [확정, 2026-11-17 이 PC에서 실행 확인]

- Python **3.13** (TensorFlow 2.21이 3.14 미지원). `py install 3.13`
- `tensorflow`, `tensorflow-hub`, `setuptools<81`(tensorflow-hub가 `pkg_resources`를 씀), `librosa`, `soundfile`, `numpy`, `scipy`
- YAMNet 출력 확인: 520 Hz 사각파 3초 → 점수 `(6, 521)`, 임베딩 `(6, 1024)`, 로그 멜 `(336, 64)`. 임베딩은 전부 0 이상, 조각 평균 + L2 정규화 후 노름 1
- `requirements.txt`의 `torch`는 쓰는 곳이 없다 → 빼는 것을 [제안]

### 6.2 합성 소리 9개로 확인한 것 (2026-11-17, 실제 알람 목록 아님)

| 520 Hz 사각파와의 코사인 | YAMNet | 로그 멜 평균 |
|---|---|---|
| 같은 520 Hz를 삑-쉼으로 끊은 것 | 0.64 | −0.25 |
| 500→3000 Hz 미끄럼 | 0.67 | −0.42 |
| 3100 Hz 순음 | 0.30 | −0.34 |
| 백색 잡음 | 0.25 | +0.59 |
| 서로 다른 쌍 36개 | 0.14~0.84, 중앙 0.58 | −0.63~0.99 |

- YAMNet은 음높이보다 리듬·종류를 본다 → 520 유사도 방식 A(임베딩 코사인)는 520 Hz 성질을 재지 못하고, **음높이는 별도 음향 특징으로 재야 한다**(⑥)
- 로그 멜 평균의 코사인은 무음·음량에 끌려가 깨진다 → 평균을 빼고 비교해야 한다
- 서로 다른 소리끼리도 코사인 중앙 0.58 → 익숙함이 넓게 번진다

### 6.3 단계

| 단계 | 입력 → 출력 | 내용 | 상태 |
|---|---|---|---|
| ① 읽기·검사 | `sounds.csv` 한 줄 → 파형 16 kHz 모노 float32 [−1, 1] | 라이선스 빈칸이면 거부(C1). **음량 맞추기**(음량 차이는 앱이 재생 볼륨으로 준다). 앞뒤 무음만 자르고 삑-쉼 사이 쉼은 유지 | [제안] |
| ② YAMNet | 파형 → 조각별 임베딩 `[N×1024]`, 점수 `[N×521]` | 조각 평균 → L2 정규화. 상위 3개 클래스(`top3`) | [확정] |
| ③ 음향 특징 | 파형 → 숫자 몇 개 | **음높이(기본음·주파수 중심, 필수)**, 홀수 배음 비율, 날카로움·거칠기 근사치 | 음높이 [확정] / 나머지 계산식은 C가 정함 |
| ④ 520 유사도 | ③ → 0~1 | **방식 C(기본음 400~650 Hz + 홀수 배음)를 기본값으로**. A·B는 비교용으로 계산만(B는 평균을 뺀 로그 멜로 고침) | [확정] (6.2 근거) |
| ⑤ 거슬림 점수 | ③ → 0~1 | 날카로움·거칠기 근사치의 정규화 조합. 평균적 경향 | 음향 추정 [확정] / 식 [제안] |
| ⑥ 밴딧 입력용 축소 | 임베딩 → k칸 | PCA. 소리 목록이 바뀌면 축이 바뀌므로 k는 작게 | **MVP 밖** |
| ⑦ 검사·쓰기 | 전부 → `sounds.json`·소리 파일·`sound-assets.ts` | C2 규칙 assert. 쌍별 코사인 분포 그림 | 기존 |

`sounds.json`에 늘어날 필드(이름은 계약 PR에서 확정): 음향 특징, 거슬림 점수, 처음 설정 화면에 보여 줄 계열 대표 여부.

### 6.4 거슬림 점수 확인 (학습 아님) [확정]

팀 3명이 소리마다 "거슬림 1~5점"을 매긴다(세 쌍 비교 E1과 같은 자리에서, 1인 약 10분). 거슬림 점수와 사람 평균의 순위 상관을 본다. 크게 어긋나면(상관 0.5 미만 [가설]) 그때 식을 고치거나 학습을 검토한다.

## 7. 앱: 두 층의 개인화 (휴대폰)

| 층 | 무엇을 맞추나 | 어떻게 |
|---|---|---|
| **구조 개인화** (7.1·7.2) | 시작 음량, 시작 단계, 대비 폭, 뺀 소리, 고른 소리 | 처음 설정 + 최근 기록에 따른 간단한 규칙 |
| **소리 개인화** (7.3~7.6) | 어떤 성질의 소리가 이 사람을 깨우나 | 밴딧 학습 |

### 7.1 처음 설정 [확정]

- 계열별 대표 소리 6개 정도를 들려주고 마음에 드는 것을 고름. **서로 다른 계열 2개 이상 권장**(⑧). 안 고르면 520 유사도 순으로 시작(⑨)
- **시작 음량**을 직접 정함: 견본 소리를 틀고 "이 크기면 깰 것 같나요?"(②·⑥)
- 부드러운 모드 켜기(대비 폭 축소, 재확인 진동만)(⑦)
- 권한 안내: 배터리 최적화 예외, 정확한 알람, 전체 화면 알림, 알림 권한. 무음·방해 금지·낮은 볼륨이면 알람을 맞출 때 경고

### 7.2 구조 개인화 규칙

- **"이 소리 빼기"** [확정]: 알람 화면과 기록 화면에 항상 있음. 뺀 소리는 후보에서 제외하고, 그 소리와 아주 비슷한 소리(코사인 상위 [가설])도 1·2단계에서 뺀다(⑦)
- **시작 단계 조정** [확정, MVP 밖]: 최근 7번 중 대부분 3단계·안전장치에서 깼으면 2단계부터 시작(①). 스누즈 비율이 높으면 안내(③)
- **아침/낮잠 구분** [확정, MVP 밖]: 낮잠 알람은 밴딧 학습에서 뺀다(⑩)

### 7.3 데이터 흐름

```
처음 설정(고른 소리, 시작 음량, 모드) ──┐
                                      ▼
기록(이벤트) ──► 밴딧 학습(매번 기록 전체로 다시 계산) ──► 소리 3개 순서 + 음량 + 이유
   ▲                                                         │
   └── 알람 재생(단계별) → 몇 번째 소리에서 몇 초 만에 껐나 ◄────┘
       → 상태 질문 → 재확인에 응답했나
```

모델 상태는 저장하지 않는다. **기록이 있으면 언제든 같은 결과**가 나오고, 순수 함수 원칙(M2)과 기존 설계("상태는 저장하지 않고 이벤트로 계산")에 맞는다.

### 7.4 밴딧 입력 특징 (재생된 단계마다)

**MVP 5개** [확정: 데이터에 비해 특징이 많으면 시작값에서 못 벗어남]

| 특징 | 출처 | 왜 |
|---|---|---|
| 상수 1 | — | 이 사람의 기본 깨움 정도(늘 스누즈하는 사람 등을 흡수) |
| 단계 위치 | 재생 기록 | 뒤 단계는 앞 소리 때문에 원래 잘 깬다. 그 몫을 소리 공으로 세지 않음 |
| 익숙함 `pHabit` | 7.5 | 익숙해서 실패한 것을 "궁합 나쁨"으로 오해하지 않음 |
| 520 유사도 | 파이프라인 ④ | 문헌의 평균적 "잘 깨움" |
| 음높이 | 파이프라인 ③ | 고음이 안 들리는 사람 등(⑥). YAMNet이 놓치는 성질 |

**MVP 밖 후보**: 거슬림 점수, 선호 유사도, 재생 음량, PCA k칸.

**원인을 구분할 수 있게** [확정]
- 음량을 단계마다 고정하지 않는다. 단계별 **범위 안에서 흔들림**(±10% [가설])을 준다. 고정하면 음량과 단계 위치가 똑같이 움직여 모델이 "커서 깼나 / 3단계라서 깼나"를 구분할 수 없다
- 같은 소리가 여러 단계에 나올 수 있게 단계별 후보 조건을 겹치게 둔다

특징은 0~1 또는 표준화한 값으로 넣는다. 밴딧이 배우는 것은 특징들의 가중치와 그 불확실성이다. 시작값(사전값)과 그것을 믿는 정도는 시뮬레이션으로 정한다 [가설].

### 7.5 익숙함 [확정: 노출 기준]

기존 식([design.md 4.2](design.md#42-점수))의 모양(비슷한 소리로 번짐, 시간이 지나면 회복, `1 − exp(−H)`)은 유지하고, 쌓이는 단위를 **나쁜 결과 수 → 들은 횟수(재생 길이 비율)**로 바꾼다. 습관화는 원래 반복 노출로 생기고, 결과의 좋고 나쁨은 이제 보상(7.6)이 따로 다룬다.

### 7.6 보상 [확정 구조 / 값은 가설]

재생된 **단계마다** 하나:

| 상황 | 보상 |
|---|---|
| 이 단계가 끝날 때까지 반응 없음 | 0 |
| 이 단계에서 끔 | `0.5 + 0.5 × exp(−그 단계에서 끄기까지 걸린 초 / τ)`, τ = 10초 [가설] |
| 다음 단계 시작 후 `graceSec` 안에 끔 | 앞 단계에 공을 줌(폰을 집는 시간). `graceSec` = 5초 [가설] |
| 이 단계에서 스누즈 | 0.3 [가설] |
| 끝까지 못 끔 | 모든 단계 0 |
| **재확인(6.7)에 응답 없음** = 다시 잠듦 | 그 알람에서 깬 단계의 보상을 0.2로 낮춤 [가설] |

- 0과 0.5 이상의 차이가 "깼나"를 정하고, 시간은 0.5~1 안에서만 더한다. 폰이 멀었던 날 같은 흔들림이 학습을 망치지 않게
- **혐오감은 보상에 넣지 않는다.** 섞으면 "잘 깨웠지만 싫었다"를 구분할 수 없다. 혐오감은 상한과 "이 소리 빼기"로 다룬다
- 재생되지 않은 단계는 기록하지 않는다

### 7.7 알람 한 번의 순서 [확정 구조 / 값은 가설]

```
1단계  편안한 소리   선호와 비슷, 거슬림 낮음(comfortCap 이하), 시작 음량 근처   ← Thompson 표본으로 고름(시도 포함)
2단계  대비 소리     1단계와 다른 성질, 거슬림 상한 안, 음량 범위 한 단계 위     ← Thompson 표본으로 고름(시도 포함)
3단계  낯선 소리     익숙함 낮음 + 1·2단계와 다름 + 거슬림 상한 안,              ← 예측 평균으로 고름(시도 없음)
                    음량 범위 한 단계 위(최대 상한보다 낮게)
안전장치            3단계도 실패하거나 앱 화면이 일정 시간 안에 안 열리면 라이브러리 기본 알람음
```

- 3단계는 **세기가 아니라 낯섦**으로 깨운다 [확정]. 근거: 습관화 연구의 탈습관화(새 자극이 반응을 되살림). Thompson·Spencer 1966 원문은 [미확인](D10)
- "익숙함 낮음" = `pHabit < habituatedAt`(기존 C9 값 재사용) [제안]
- 음량: 시작 음량(7.1)에서 단계마다 한 범위씩 올림, 범위 안 흔들림(7.4), 최대 상한 config [가설]
- 부드러운 모드: 2단계 대비 폭을 줄인다(⑦)
- 최근 제외(`recentExclude`)는 1·2단계에 적용. "이 소리 빼기"는 모든 단계에 적용
- 후보가 비면 정해진 순서로 조건을 풀고 무엇을 풀었는지 기록(기존 `fallback`과 같은 방식). 거슬림 상한과 "이 소리 빼기"는 풀지 않는다
- Thompson 표본의 시드는 호출하는 쪽이 넘긴다(예: 알람 ID + 날짜). 같은 시드면 같은 순서(M2)
- 단계 길이 30초 [제안], 대비를 재는 방법(음량·음높이·거칠기 축 / YAMNet 거리) **[열림]**
- 안전장치까지 간 비율을 사람별로 기록한다(①)

### 7.8 끈 뒤: 상태 질문과 재확인 [확정]

```
끄기 → "지금 어떠세요?"
   😴 아직 졸려요      → 3분 뒤 부드러운 소리로 재확인
   🚶 일어나는 중이에요 → 7분 뒤 알림 "일어나셨나요?"
   ☀️ 완전히 깼어요    → 끝
   (응답 없음)         → "일어나는 중"과 같게 처리
재확인에 응답 없음 → 다시 잠든 것으로 보고 다시 알람 + 보상 낮춤(7.6)
```

- 재확인 시간 3분·7분은 config [가설]. 부드러운 모드면 재확인은 진동만(⑦)
- 잠결의 자기 판단은 믿기 어렵다. 상태 응답은 **보상에 쓰지 않고** 다음 행동(재확인 여부)과 확인용 기록에만 쓴다. 보상의 행동 신호는 끄기 시간과 재확인 응답이다
- 기존 "익숙했나요?" 질문(`selfReport`)은 **이 질문 하나로 바꾼다.** 아침 질문은 하나만 둔다
- 상태 응답과 재확인 결과가 얼마나 자주 어긋나는지 기록한다(기존 E4의 역할)

### 7.9 스누즈 [제안]

스누즈하면 순서를 멈추고 `snoozeMin` 뒤 2단계부터 다시 울림. 스누즈 상한 2회, 넘으면 다음 울림은 3단계부터.

### 7.10 AI가 내놓는 것

| 결과물 | 쓰이는 곳 |
|---|---|
| 소리 3개 순서 + 단계별 음량 | 알람 재생 |
| 소리별 예상 깨움 점수 | 고르는 기준, 이유 화면 |
| 이유 한 줄(가중치에서 만듦, 예: "저음에 잘 깨셨어요") | 이유 화면 (기존 범위 "되면 좋음" → **반드시**) |
| 사람별 프로필(특징별 가중치와 확신) | 통계 화면, 발표 시연 |

**AI가 학습하지 않는 것**: 소리 특징·거슬림 점수(오프라인 고정), 익숙함(식), 순서 규칙·구조 개인화(규칙).

## 8. 알람 재생 경로 [확정 ①, 동작은 미확인]

알람 라이브러리가 울리면 잠금 화면 위로 앱의 알람 화면이 열리고, 앱이 expo-audio로 단계별 소리·음량을 바꿔 튼다. I-1에서 확인할 것([issues-draft.md](issues-draft.md) I-1):

1. 앱이 꺼진 상태에서 예약 시각에 울리나 (후보: react-native-alarm-scheduler, react-native-notify-kit. notifee는 2026-04 보관 처리) [미확인]
2. 울릴 때 잠금 화면 위로 앱 화면이 열리나 [미확인]
3. 열린 화면에서 expo-audio로 소리 2개를 바꿔 트나 (`player.replace`, `volume`은 SDK 58 문서에 있음)
4. **미디어 볼륨 0일 때** 어떻게 되나. expo-audio가 알람 볼륨이 아니라 미디어 볼륨을 쓸 가능성 → 안전장치 필요 [미확인]
5. 재확인 알림(7.8)을 몇 분 뒤에 띄우고 응답을 받나

안 되면: 알람마다 소리 하나(기존 설계)로 두고, 순서 대신 알람 사이에서 같은 규칙을 적용한다.

## 9. 확인 방법

- **단위 테스트(jest-expo)**: 보상 계산(재확인 무응답 포함), 익숙함, 순서 규칙(3단계는 같은 입력에 같은 결과, 거슬림 상한을 넘거나 뺀 소리는 절대 안 나옴), 시드가 같으면 같은 순서, 음량 흔들림이 범위 안
- **시뮬레이션(동작 확인용, 효과 주장 아님)**: 앱의 추천 함수를 그대로 써서 5절의 **①②③⑥⑦** 다섯 유형을 14일씩 돌린다. 유형마다 그리는 것: 깬 단계 평균, 안전장치까지 간 비율, 다시 잠든 비율, 쓴 소리 수, 학습한 가중치가 정답 쪽으로 가는지(특히 ⑥의 음높이), 쓸 수 있는 낯선 소리 수. 파이썬으로 다시 구현하지 않는다(두 구현이 어긋나는 위험)
- 실사용 기록(팀 3명): "동작한다"는 확인만

기존 실험의 변화: E1 유지(+ "다른 공간이 10%p 이상 높지 않으면 YAMNet 유지"를 미리 정함 [제안]), E2 기본값 C, **E3 삭제**(밴딧이 대신함), **E4는 상태 응답 ↔ 재확인 비교로 바뀜**, E5는 시뮬레이션으로 대체, **E6 추가**(6.4 거슬림 확인).

## 10. 한계 (발표에서 정직하게)

- 대회 기간 기록으로는 가중치가 시작값 근처에 머물 가능성이 크다. 시연은 시뮬레이션으로 "학습이 이렇게 움직인다"를 보여 주고, 실사용 기록은 동작 확인으로만 쓴다
- 수면이 불규칙한 사람(⑤)은 학습이 느리다
- 오래 쓰면 "바뀌는 알람" 자체에 적응할 수 있다(⑪). 소리 목록이 고정이라 근본 대책이 없다
- 잠결에 끄는 순간은 막지 못하고, 재확인이 몇 분 뒤 잡는다(④)
- 같이 자는 사람, 앱 재설치 시 학습 소실(익명 인증, AD6)
- 거슬림 점수는 평균적 경향이다. 개인의 혐오감은 "이 소리 빼기"로만 반영한다

## 13. MVP (마감 안에 꼭)

소리 목록(I-3) → 파이프라인 ①②③④⑤⑦ → 밴딧(특징 5개) + 익숙함(노출 기준) + 보상 + 3단계 순서 규칙 → 처음 설정(소리 선택, 시작 음량) + "이 소리 빼기" → 알람 재생 경로(8절 1~5 확인) → 상태 질문·재확인 → 이유 화면 → 시뮬레이션 그래프(①②③⑥⑦).

MVP 밖(시간이 남으면, 못 하면 한계로 기록): 파이프라인 ⑥ PCA, 거슬림 사람 평가(E6), 시작 단계 자동 조정, 아침/낮잠 구분, 부드러운 모드, 통계 화면, 선택 기능 미션.
